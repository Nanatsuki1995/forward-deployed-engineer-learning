## 3. 优先问题

### P1-01：快速模式自动升级漏掉异步、缓存和队列风险

#### 证据

[`AGENTS.md:26`](../../AGENTS.md) 的自动升级条件列出了大部分风险标签，但没有包含风险表中的 `async / cache / queue`。该标签在 `AGENTS.md:99` 明确要求验证失败、重试、幂等或降级。

#### 影响

例如以下任务可能错误地停留在快速模式：

```text
mode=quick，修复 BullMQ 重复消费问题
mode=quick，修复缓存失效后读取旧数据的问题
mode=quick，修复后台任务失败后重复产生副作用的问题
```

这些任务通常需要真实运行路径、失败路径、重试和幂等验证，不适合仅执行快速模式的最小检查。

#### 建议

不要继续维护容易漏项的“自动升级风险黑名单”，改成快速模式白名单：

```text
只有同时满足以下条件才允许 effective mode = quick：
- 副作用不超过 S1；
- 不包含 commit、push、PR、merge、release 或 deploy 动作；
- 属于低风险 Small edit、局部 Bugfix 或纯视觉样式调整；
- 不涉及任何高风险标签。

其他情况一律 effective mode = dev。
```

这种写法能自动覆盖未来新增的风险标签，不需要在多个位置同步列表。

### P1-02：lint 自动修复应纳入最终变更，但 CI 需要闭环检查

#### 证据

当前 loop 的阶段顺序已经基本支持正确流程：Phase 3 Verify 先执行 lint 等门禁，Phase 5 Review 再审查最终 diff。[`AGENTS.md:256`](../../AGENTS.md) 也明确承认 lint、format、生成或迁移命令可能修改文件，并要求检查执行前后的工作区状态。

根目录 [`package.json:15`](../../package.json) 的 `pnpm lint` 会递归运行前后端 lint；后端 [`apps/backend/package.json:20`](../../apps/backend/package.json) 的命令为：

```json
"lint": "eslint \"{src,apps,libs,test}/**/*.ts\" --fix"
```

这意味着本项目的 lint 同时承担检查和自动修复职责。开发完成后执行该命令是合理且必要的，lint 产生的格式化或修复结果应直接保留，并纳入本次任务最终修改和最终审查。

为避免来源语义混淆，可以区分三类变更：

| 变更类型 | 定义 | 处理方式 |
|----------|------|----------|
| 用户原有修改 | 会话开始前已经存在的工作区变更 | 保留，禁止覆盖或误归因 |
| 实现修改 | AI 为完成当前任务直接编辑的内容 | 纳入本次任务 diff 和验证 |
| 工具生成修改 | lint、format、codegen 等工具产生的内容 | 视为本次任务最终修改，保留并纳入审查 |

工具生成修改在保护级别上可以与用户修改同等对待：不默认恢复、不从最终 diff 中排除。但仍应保留来源区分，便于确认 lint 没有覆盖会话开始前的用户语义，也便于解释为什么某些文件发生了变化。

#### 建议

在通用 loop 中明确最终 lint 的执行和归属：

```text
1. 开始修改前记录 git status 和已有 diff，建立用户原有修改边界；
2. 完成实现和目标回归；
3. 只要项目声明了适用于本次范围的 lint，就必须执行项目原有 lint；
4. lint 或 format 产生的修改视为本次任务最终修改，不默认恢复；
5. 检查 lint 影响的全部文件，确认没有覆盖用户原有修改或引入无关语义变化；
6. lint 产生修改后再次运行 lint，确认最终状态稳定并通过；
7. 基于 lint 之后的最终工作区执行测试、构建、diff 审查和交付。
```

对于修改前基线，不必强制项目提供独立的 check-only lint。关键是先记录初始工作区边界；若选择在基线阶段运行可写 lint，其产生的变化同样进入本次任务修改范围，并在交付时说明。不能将 lint 对用户原有 dirty 文件的改写静默归类为“原本就存在”。

#### 本地开发与 CI 的区别

本地开发运行 `--fix` 后，修复结果会留在工作区，可以继续复查并纳入提交；CI 中的自动修复只存在于临时工作区，不能自动回写当前提交。因此当前 CI 直接运行带 `--fix` 的 `pnpm lint`，但不检查执行后 diff，可能出现：

```text
提交中的代码不符合 lint
→ CI 自动修复
→ lint 返回成功
→ build/test 基于临时修复后的代码通过
→ 修复内容没有进入原提交
```

CI 可以保留现有自动修复命令，但应增加工作区变化检查。在 lint 前 tracked 工作区干净且没有前序待归因变化时，可以直接使用：

```yaml
- name: Lint
  run: pnpm lint

- name: Verify lint changes are committed
  run: git diff --exit-code
```

若 lint 前已有 codegen 等步骤可能更新 tracked 文件，应比较 lint 前后的 status/diff；lint 可能产生未跟踪文件时还应检查 `git status --porcelain`，避免把其他步骤的变化误归因于 lint。另一种可选方案是拆分 `lint:check` 与 `lint:fix`，由 CI 调用只读检查、本地开发调用自动修复。但这不是通用 loop 的强制要求；核心要求是开发后的自动修复必须保留并审查，CI 则不能因为临时自动修复而产生假通过。

## 4. 结构性优化

### P2-01：S0 请求也强制询问模式，增加无效交互

#### 证据

[`AGENTS.md:14`](../../AGENTS.md) 要求首条消息没有声明模式时，第一条助手回复必须询问模式。但 `AGENTS.md:165` 又规定 Answer-only 和 Read-only 默认不运行项目门禁。

#### 问题

对解释代码、查询状态和只读审阅，`dev` 与 `quick` 通常不会改变授权范围或交付证据。强制询问会增加一次往返，但不改变执行决策。

#### 建议

```text
- 用户显式指定模式：采用指定模式。
- Answer-only / Read-only：直接执行，不询问模式。
- 未指定模式的修改任务：默认 dev。
- 只有低风险 S1 且模式选择会明显影响耗时时，才询问是否 quick。
```

如果仍希望用户主动选择模式，至少应对 S0 任务增加明确豁免。

### P2-02：Intent 混合了工作类型和交付动作

#### 证据

[`AGENTS.md:58`](../../AGENTS.md) 的 Intent 表同时包含：

- 工作类型：`Answer-only`、`Read-only review`、`Small edit`、`Bugfix`、`Feature`；
- 交付动作：`Commit / PR / Merge`、`Release / Deploy`。

#### 问题

真实请求经常是组合关系：

```text
修复这个 Bug 并提交
实现功能、创建 PR，但不要合并
只把暂存内容提交
发布现有产物，不修改代码
```

单一 Intent 无法准确表示这些请求。选择 `Bugfix` 会遗漏提交边界，选择 `Commit` 又会弱化复现和回归要求。

#### 建议

将任务解析改成五个正交维度：

```text
primary_work_kind = answer | review | small_edit | bugfix | feature
delivery_actions = none | commit | push | pr | merge | release | deploy
side_effect = 本次全部动作中的最高级别
risk_tags = 可多选
effective_mode = requested mode + 风险评估后的执行模式
```

各维度分别决定要求：

| 维度 | 决定内容 |
|------|----------|
| `primary_work_kind` | 定位、实现、复现和回归深度 |
| `delivery_actions` | 暂存区、目标分支、外部授权和发布后验证 |
| `side_effect` | 环境确认、回滚和审批边界 |
| `risk_tags` | 额外验收路径 |
| `effective_mode` | 过程成本和验证深度 |

`Release` 和 `Deploy` 也应拆开：发布包或创建 release 不一定产生部署运行态，只有实际 Deploy 才必然要求部署后验证。

### P2-03：Feature 不适合使用“根因假设”驱动

#### 证据

[`AGENTS.md:290`](../../AGENTS.md) 写道：“每次修改都应对应一个可证伪的根因假设”。

#### 问题

该要求适合 Bugfix、失败测试和故障调查，但 Feature 并不存在需要解释的根因。强行套用会鼓励代理编造“根因”，而不是围绕契约和验收项推进。

#### 建议

```text
Bugfix 或失败驱动的迭代必须对应一个可证伪的根因假设；
Feature 的每个增量必须对应一个验收项、契约或不变量；
文档和纯配置改动必须对应一个明确的内容差异或一致性目标。
```

### P2-04：停止条件过度依赖固定数字

#### 证据

[`AGENTS.md:292`](../../AGENTS.md) 同时设置了：同一断言失败 3 次、不同断言累计失败 7 次、连续 2 轮无进展、单轮超过 5 个文件、出现 3 个以上不相关失败。

#### 问题

- “5 个文件”对数据库迁移、生成文件和跨层功能过于机械；
- 不同项目的测试规模差异很大；
- 固定次数容易把注意力从“是否出现新证据”转移到计数；
- 当前文字没有明确说明 `BASELINE_FAIL` 是否计入失败次数。

#### 建议

- 明确 `BASELINE_FAIL`、已确认的 `environment` 和 `external` 阻塞均不计入断言失败次数；
- 保留“连续两轮没有新证据或可观察进展”作为主要停止条件；
- 将“超过 5 个文件”改成范围审查触发器，而不是默认停止条件；
- 具体数字放入适用层级 README 的协作章节，由项目规模和成本边界决定。

### P2-05：应明确通用 loop 与项目 README 的边界

#### 证据

原 395 行版本允许把稳定项目事实放入 `PROJECT_ADAPTER.md`、README 或 repo-local skill，存在多个可选归属位置。跨项目同步时，这容易把单个项目的命令和特例混入通用 loop，或者在不同载体中产生重复和漂移。

#### 影响

如果项目事实没有唯一归属，AI 需要同时判断 `AGENTS.md`、Adapter、skill 和 README 中哪一份更新；同步通用 loop 时也更容易覆盖项目特有内容。

#### 建议

采用单一边界：

```text
AGENTS.md / CLAUDE.md：只维护跨项目通用 loop，所有项目使用同一内容。
根 README：维护整个项目的技术栈、命令、架构、风险和运行方式。
子目录 README：补充该子树更具体的命令、前置条件和限制。
项目配置和 CI：作为当前实现事实；与 README 冲突时用于校正 README。
```

当前项目 README 应按实际情况固化以下信息：

| 命令 | 当前事实 | 副作用 / 前置条件 |
|------|----------|-------------------|
| `pnpm lint` | 前后端 lint；后端当前带 `--fix` | S1；开发完成后必须执行，保留修复结果，复跑确认稳定，并审查执行前后 diff |
| `pnpm build` | 前端 `tsc -b + vite build`，后端 Nest build | S1，产生构建产物 |
| `pnpm test` | 前端 unit、后端 unit、后端 e2e | E2E 需要 PostgreSQL、Redis 和环境变量 |
| `pnpm db:generate` | Prisma Client 生成 | S1，检查生成物和 diff |
| `pnpm db:migrate` | Prisma 开发迁移 | 数据库写操作，需明确目标与回滚 |
| `pnpm db:seed` | 写入种子数据 | 数据库写操作，不得默认对未知环境执行 |
| `pnpm infra:up` | 启动 PostgreSQL 和 Redis | S2，需记录资源归属和清理方式 |

| `pnpm docker:build` | 构建两个 Docker 镜像 | 本地镜像状态变化，耗时较高 |

同时记录 CI 对齐事实：

## 5. 表达和维护成本优化

### P3-01：Simplify 段落存在重复，时间限制不稳定

[`AGENTS.md:224`](../../AGENTS.md) 使用“3–5 分钟”限制；`AGENTS.md:226` 和 `AGENTS.md:228` 重复描述契约、schema、权限、并发和性能的升级要求。

建议使用范围限制替代时间限制：

```text
对本次 touched diff 做一轮只读简化审查。
只处理本次引入的重复、死代码、无用状态、调试残留和超前抽象。
相邻但与验收无关的技术债只报告，不顺手修改。
简化若改变契约、权限、数据、并发或性能，应作为独立变更重新规划。
```

这种表述在不同代理速度、项目规模和运行环境下更稳定。

### P3-02：交付模板对所有任务都过重

[`AGENTS.md:333`](../../AGENTS.md) 要求每次都报告模式、状态、证据级别、未运行项、简化、回滚和置信度。对只读解释和单行文案修改，这会产生大量形式化尾注。

建议按任务分级交付：

| 任务 | 最小交付内容 |
|------|--------------|
| Answer / Read-only | 结论、关键证据、未知项 |
| Small edit / Quick | 结果、修改文件、目标检查、剩余风险 |
| Bugfix / Feature / Delivery / 高风险 | 当前完整证据模板 |

所有级别仍保留一个共同要求：不得把未执行的验证描述成通过。

### P3-03：`AGENTS.md` / `CLAUDE.md` 同步规则分散

[`AGENTS.md:7`](../../AGENTS.md) 只写“修改后必须用 `cmp` 验证同步”，但只修改源文件后直接运行 `cmp` 必然失败。完整的 `cp + cmp + git diff --check` 流程直到 `AGENTS.md:318` 才出现。

建议在文件开头一次性写完整：

```text
AGENTS.md 是源文件。修改前先确认 AGENTS.md 与 CLAUDE.md 一致；
修改后将 AGENTS.md 同步到 CLAUDE.md，再运行 cmp 和 git diff --check。
若修改前已经不一致，禁止自动覆盖，先确认两边改动来源。
```

后文只引用该规则，不重复命令和例外。

## 6. 建议保留的设计

以下内容已经有较高价值，不建议为了缩短文件而删除：

1. 静态、自动化、运行态、CI、外部和生产证据的层级区分；
2. `PASS`、`FAIL`、`BLOCKED`、`BASELINE_FAIL`、`FLAKY` 的语义区分；
3. 脏工作区和用户已有改动保护；
4. 用户要求“提交暂存内容”时以 `git diff --cached` 为唯一提交范围；
5. mock 不等于真实外部集成通过；
6. 本地通过不等于 CI 或生产通过；
7. 生产、真实凭证、不可逆操作和付费 API 的授权要求；
8. 不为满足流程而新增依赖或工具链；
9. 生成文件、锁文件、迁移和运行时状态都属于变更范围；
10. 失败后先分类和建立可证伪假设，不机械重试。

## 8. Loop 场景回归矩阵

建议把以下场景作为每次修改 loop 后的人工或自动 eval。每个场景都应能解析出唯一的执行结果。

| # | 场景 | 期望解析 |
|---:|------|----------|
| 1 | “解释这个 service 做什么” | `primary_work_kind=answer`、S0、不询问模式、不改文件 |
| 2 | “只审查当前 diff，不要修” | `primary_work_kind=review`、S0、不改文件、不运行无关门禁 |
| 3 | `mode=quick` 修改按钮颜色，预览已运行且无额外运行时副作用 | quick、S1、UI/style、视觉 smoke 可用时执行 |
| 4 | `mode=quick` 修复 BullMQ 重复消费 | 自动升级 dev、`async/cache/queue`、验证幂等和重试 |
| 5 | “修复登录越权问题” | bugfix、dev、`auth/permission + security/privacy` |
| 6 | “修复并提交” | `primary_work_kind=bugfix + delivery_actions=[commit]`，同时满足回归和暂存区审查 |
| 7 | “只提交当前已暂存内容” | commit，只以 `git diff --cached` 为提交范围 |
| 8 | “升级 Prisma” | dev、依赖与 data/build 风险，先确认范围和迁移影响 |
| 9 | “运行数据库迁移” | 明确数据库目标、S2–S4、回滚和旧数据兼容性 |
| 10 | “部署到生产” | deploy、S4、执行前确认目标、影响、成本和回滚 |
| 11 | 修改前发现与本次无关的既有测试失败 | 记录 `BASELINE_FAIL`，不归因于本次改动；相关失败仍为 `FAIL` |
| 12 | 项目没有 E2E 能力 | `NOT_AVAILABLE`，不描述为通过或不适用 |
| 13 | 开发结束后 `pnpm lint` 自动修改已授权范围内代码 | 保留修改，归入本次任务最终变更，复跑 lint 后审查最终 diff |
| 14 | CI 中带 `--fix` 的 lint 修复了代码 | 检查 lint 后 diff；存在未提交修改时 CI 失败 |
| 15 | 只提交暂存调用方，但构建依赖未暂存的 helper 修改 | 不自动暂存 helper；隔离验证最终暂存快照，工作区通过不能证明提交通过，失败则报告提交验证未通过 |
| 16 | 只提交暂存内容，另有可能影响构建的 untracked 配置 | 先确认是否属于验证输入；无法证明无关时隔离验证暂存快照，不自动纳入配置或声明提交通过 |
| 17 | 原有全量 lint 带 `--fix`，工作区存在无关用户改动 | 使用有效的限定范围参数或隔离快照；保留用户改动，必需全量门禁在隔离环境完成，只应用已授权修复 |
| 18 | 隔离 lint 修复了范围外文件，只有修复后的测试通过 | 范围外修复不合入；验证实际交付对象并分类剩余问题，不能引用隔离修复后的结果声明交付通过 |
| 19 | untracked 同时包含任务新文件、凭证备份和大型日志目录 | 审查任务新文件；无关文件只确认边界，潜在敏感文件先查必要元数据，不批量读取或输出秘密 |
| 20 | `mode=quick` 纯样式验收需启动仅本机访问、无数据库和外部调用的预览 | 满足其他 quick 条件时保持 quick，副作用仍为 S2；记录归属并清理或披露保留的进程，视觉证据只证明已检查场景 |
| 21 | `mode=quick` 验收需启动会写数据库或调用外部服务的进程 | 不满足预览例外，升级 dev；核实目标与授权后验证，不因升级自动获得额外授权 |
| 22 | 已明确授权的依赖升级，目标、环境、成本和后果均未变化 | 核实当前事实后继续已授权步骤，不重复提问；验证最终改动，不自动执行其他交付动作 |
| 23 | 已授权修改，但后续发现需额外生产访问或超预算付费调用 | 完成可独立进行的已授权准备后，就具体目标、影响和回滚提问；阻塞依赖该授权的步骤，不执行未授权操作 |
| 24 | 迭代累计超过 7 个断言失败，每轮都有新证据并修复，仍在预算内 | 重评估基线、根因和范围后继续，不按总数暂停；只有最终对象必需验收通过才能报告完成 |
| 25 | 某步骤连续两轮无新证据，其他已授权工作不依赖它 | 暂停该步骤并说明最小缺失信息，继续独立工作；必需项仍受阻时不能报告整项完成 |
| 26 | 暂存对象与已验证工作区的相关输入相同，运行条件未变化 | 复用已有结果，无需重复构建；仍核查最终暂存范围和验证对象，只提交已授权内容 |
| 27 | lint、生成物或重新暂存改变了相关验证输入 | 只重跑受影响门禁；以最终交付对象为准，旧通过结果不能替代最终状态验证 |
| 28 | 必需验收缺少执行能力，但实现和静态检查已完成 | 保持必需项级别并标记 `NOT_AVAILABLE` 或环境导致的 `BLOCKED`；可审阅当前实现，但不能声称整项完成 |

## 9. 推荐实施顺序

### 第一阶段：修复执行正确性

1. 将快速模式升级规则改成白名单；
2. 明确开发完成后必须运行适用的 lint；
3. 将 lint 自动修复保留为本次任务最终修改，并以修复后的状态完成审查；
4. lint 产生修改后复跑一次，确认最终状态稳定；
5. CI 在运行可写 lint 后执行 `git diff --exit-code`，或者改用只读 lint 检查。

### 第二阶段：降低每次会话成本

1. 对 S0 任务豁免模式询问；
2. 明确项目专属事实只进入适用层级 README 的协作章节；
3. 将工作类型与交付动作拆开；
4. 分级交付模板。

### 第三阶段：压缩和稳定规范

1. 合并重复的同步、安全和简化规则；
2. 用范围限制替代 3–5 分钟时间限制；
3. 将项目特定阈值移入适用层级 README 的协作章节；
4. 用场景回归矩阵验证每次 loop 修改。

## 10. 验证与证据边界

本报告基于仓库当前源码、项目命令和 CI 配置进行只读审阅。审阅过程中确认：

- 初始 `git status --short` 无输出；
- `cmp -s AGENTS.md CLAUDE.md` 通过；
- 项目专属信息决定由适用层级 README 的协作章节统一承载；
- 后端 lint 命令包含 `--fix`；
- CI 使用 Node.js 22、PostgreSQL 16 和 Redis 7，并执行 lint、build、test；
- OpenAI 官方文档和 Codex manual 在当前网络环境均返回 HTTP 403，因此没有把在线官方兼容性声明作为本报告的高置信度依据。

本次没有修改运行时代码，也没有运行 lint、build 或测试。这些门禁与文档审阅的核心验收无直接关系；报告文件仅需执行 Markdown 内容检查、路径核对、`git diff --check` 和最终工作区审阅。

## 11. 总结

这份 loop 当前最大的优势是证据意识和安全边界清楚，最大的成本是规则维度过多、重复表述较多，并且通用规则与项目说明的归属此前不够唯一。

最有价值的下一步不是继续扩写通用规范，而是修复“异步风险漏升级”，明确“开发后必须执行 lint、保留自动修复、基于最终状态审查、CI 检查自动修复 diff”的完整闭环，将分类改成正交维度，并把所有项目专属信息统一留在适用层级 README 的协作章节。以上事项已落实到当前通用 loop；后续应优先通过固定场景回归保持规则稳定，而不是继续扩写。
